# Generators

`node generator/huff/generate.ts [--hardfork <name>] [t ...]` builds the Poseidon2 BN254 Huff permutation and `node generator/yul/generate.ts [t ...]` the Yul library for a state width t (2, 3, 4, 8, 12). The hardfork (`huff/fork.ts`: paris, shanghai, cancun, prague, osaka, amsterdam; default shanghai) sets the opcodes the Huff emitter may use and the code size limit; a fork other than the default writes to `src/bn254/huff/<fork>/` and `test/<fork>/`, and `FOUNDRY_PROFILE=<fork> forge test` runs those tests on that EVM. `npm run generate:huff:amsterdam` builds t = 16, 20, 24, 28 with the EIP-8024 `DUPN` / `SWAPN` opcodes, `npm run generate:huff:osaka` builds the same widths as chains of contracts under the EIP-170 code size (`huff/split.ts`), `npm run generate:huff:paris` builds t = 3 without `PUSH0`.

- `field.ts`, `params.ts`, `reference.ts`, `value.ts`, `vectors.ts`: shared by both generators (field arithmetic, parameter derivation, BigInt reference permutation, bound-tracked values with the opcode semantics, test inputs). `test-reference.ts` checks the first three.
- `huff/`: `generate.ts` (CLI), `fork.ts`, `schedule.ts`, `split.ts`, `emitter.ts`, `render.ts`.
- `yul/`: `generate.ts` (CLI), `schedule.ts`, `program.ts`, `render.ts`.

Both generators simulate what they emit: every value carries an exact upper bound (`value.ts`), an `ADD` / `MUL` / `SHL` is refused when the bound could exceed 2^256 - 1, and the outputs of the simulated code are compared with `reference.ts` on the inputs of `vectors.ts` before any file is written (each part of a split permutation against `permutationSteps`, its own rounds). The Huff emitter simulates the stack as well (reach, depth, gas, size, the memory copies of values out of reach; the reach is 16 with the legacy opcodes and 235 from Amsterdam); the Yul program emits nested expressions and lets, models the reach of every local for the literal (optimizer off) legacy compile and leaves the rest to solc (see [src/bn254/README.md](../src/bn254/README.md#yul-generator)). `compat-check.sh` compiles a consumer of every Yul library in each compiler mode.

## Evidence that the output matches other implementations

The generated code follows the [Poseidon2 paper](https://eprint.iacr.org/2023/323). Its constants are generated by `params.ts`, a port of the HorizenLabs [`poseidon2_rust_params.sage`](https://github.com/HorizenLabs/poseidon2/blob/bb476b9ca38198cf5092487283c8b8c5d4317c4e/poseidon2_rust_params.sage) script. The constants and permutation outputs match these other implementations.

For t = 4 the Huff and the Yul are the `hash_*` sponge contracts. `reference.ts` reproduces the permutation KAT on [0, 1, 2, 3] in [Barretenberg](https://github.com/AztecProtocol/aztec-packages/blob/8c7eb07b84eda9bcb3951fbacaa3529f6a726ae6/barretenberg/cpp/src/barretenberg/crypto/poseidon2/poseidon2_params.hpp#L447-L458) and [TACEO co-snarks `t4_kat1`](https://github.com/TaceoLabs/co-snarks/blob/f6c5a16dff0c5978496f3c2511115c9b8654e7d0/mpc-core/src/gadgets/poseidon2/poseidon2_permutation.rs#L378) (4/4). TACEO (Rust / Noir), Polygon pil2 (C++) and gnark-crypto (Go) each implement the permutation separately. The constant tables all come from the same HorizenLabs script, so this shows a faithful port of that script, not an independent derivation of the parameters.

## Not covered

- The script's subspace-trail checks (`algorithm_1/2/3`) are not ported. They only abort, never change constants, and the matching tables above were generated by the script.
- For t != 4 the Foundry tests are 8 fixed vectors plus input sanitisation, and the Yul tests fuzz the Yul permutation against the Huff one (1,000 runs). Only `vector_0` is externally sourced, and for t = 20, 24, 28 (Amsterdam and Osaka Huff) not even that: those widths rest on the shared `params.ts` / `reference.ts` alone. Overflow safety rests on the bound check in `value.ts`, which holds for all inputs.
- `node generator/test-reference.ts` gates t = 3 and t = 4 only. The t = 2, 8, 12 comparisons above were run by hand.
