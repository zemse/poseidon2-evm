# Poseidon2 for BN254

This is an instance of Poseidon2 for the BN254 curve (also known as alt_bn128).

**Compatible with:** [Noir](https://noir-lang.org/) / [Barretenberg](https://github.com/AztecProtocol/barretenberg) / [Aztec](https://aztec.network/) ecosystem.

## Recommendation

Using the Yul library is recommended for most use cases. It provides the best gas efficiency when inlined into your contracts.

For external calls to deployed contracts, the Huff implementation provides the lowest gas cost. The Huff source targets Amsterdam (it uses the EIP-8024 `DUPN` / `SWAPN` opcodes) and does not run on earlier forks; the contracts deployed from v2 and earlier (`deployed-artifacts/`) are pre-Amsterdam builds.

## Notes on Optimizations

### ADDMOD Optimization

This optimization is used in Yul and Huff implementations. Not used in Solidity.

Using `ADD` is cheaper (3 gas) compared to `ADDMOD` (8 gas) which also needs a prime argument (3 gas to duplicate on stack), saving 8 gas per instance. Using `ADD` instead of `ADDMOD` overflows the value beyond the field domain but we can `MOD` the value or use it with `MULMOD` which outputs a legal value.

Applying this optimization for the BN254 curve is tricky because the PRIME is almost close to uint256 max, which means the value could overflow the uint256 variable, corrupting the state and leading to an incorrect hash value. For other curves with smaller prime fields, this optimization is trivial.

BN254 prime allows adding 5 field values (4 additions, since 2^256 / p is about 5.29). Both the Yul and the Huff code are generated. `generator-rs/src/value.rs` for Yul and `generator-rs/src/huff/emitter.rs` for Huff carry inclusive upper bounds and reject lazy operations that could exceed 2^256 - 1. Which value to reduce matters: the generic t = 2 `internalReduceOutputs` policy keeps the sum lazy and reduces the inactive output, whereas the selected Huff `internalMul3` path computes `(3*s1 mod P) + s0^5`, keeping the inactive output below 2P and the next active constant addition below 5P; its first round, whose inactive input the external rounds leave below 3P, reduces the active output with an ADDMOD on a second PRIME copy instead of the generic shared-sum bridge (94 gas instead of 105). The selected t = 3 Huff templates use periodic reductions rather than reducing both inactive outputs every round. The generated code is also executed on test vectors against the BigInt reference before it is written.

If there is even a single situation where an unsafe addition could overflow uint256 max, then it is possible for an attacker to vanity mine the input. The published v1.0.0 Yul had such an addition (hand-tracked in comments); `test_regression_overflow_counterexamples` locks in the inputs that exposed it.

### No Stack Scheduling

This optimization is used in Huff. Not used in Yul or Solidity.

The EVM has a stack limit of 1024. Hence, compilers are designed to avoid running into stack overflow by scheduling every element pushed on the stack to be used later. This involves calling a bunch of `SWAP` opcodes to rearrange the stack before calling an internal function.

However, it is cheaper to not rearrange elements on the stack and instead `DUP`licate them in the order we want. This works when we are working with fewer than 16 variables (including temporary) because we have `DUP1` to `DUP16`.

This instance of Poseidon2 has 64 total rounds. The generator balances in-place consumption against leaving dead values below the live state; the selected t = 4 raw permutation reaches 94 stack slots. On Amsterdam `DUPN` / `SWAPN` reach slot 235, so the dead values can stay deeper than 16; from t = 16 the internal rounds consume the old state in place (`internalConsume`, below), which beats collecting it within the 1024 limit.

### Huff Generator

`poseidon2-gen huff` (`generator-rs/`, shared modules in `generator-rs/src/`, Huff-specific ones in `generator-rs/src/huff/`) builds the Huff permutation for a state width t:

- `round_constants.rs` ports the HorizenLabs `poseidon2_rust_params.sage` script: round numbers, Grain LFSR round constants and the internal matrix diagonal with its minimal polynomial check. Both generators first run `assert_known.rs`, whatever width they build: t = 4 against `constants.ts`, the Barretenberg KAT and the sponge vectors, t = 3 against the HorizenLabs instance, permutation KATs from TACEO for t = 2, 4, 8, 12, 16, sample gnark-crypto constants for t = 8, 12, 16, and the round numbers against the paper, each pinned to a commit permalink.
- `reference.rs` is the reference permutation.
- `huff/emitter.rs` is a symbolic stack simulator. Every value carries an inclusive upper bound; `ADD` and `MUL` are only emitted when the bound stays below 2^256, otherwise `ADDMOD` / `MULMOD`. It also tracks depth, the deepest `DUP`, gas and bytecode size, and executes the emitted stream on test inputs. The hardfork (`huff/fork.rs`, `--hardfork <name>`) sets the reach: `DUP16` / `SWAP16` for the legacy opcodes, slot 235 with the EIP-8024 `DUPN` / `SWAPN` of Amsterdam (3 gas and 2 bytes each, so the one-byte opcodes are still preferred up to 16). A value the reach cannot `DUP` can be shadowed: stored to a memory slot when produced and loaded from there instead (see Osaka below).
- `huff/schedule.rs` orders the field operations like the hand-written code did (results land on top, operands are pre-placed so results land in place) and tries a few option sets per t (diag constants in memory, garbage collection, two forms of the t = 4k linear layer, which value the internal round reduces, how PRIME copies are supplied and retained, whether the internal rounds consume the old state in place, whether the steady internal rounds share one body reached by `JUMP`, and in sub-chains of what length when that body would not fit, whether the external rounds of t <= 4 and the internal rounds of t = 4 follow the stack programs of `huff/templates.rs`), keeping the cheapest one that fits. The programs are searched by `generator-rs/stacksearch/` with A\* over configured graphs (a lane's S-box is one macro move, with swap sequences from a table). The graphs and their generation filters restrict the search; resource-limited runs are not exhaustion certificates, and no unrestricted EVM optimum is claimed. The t = 3 re-entry costs 189 and both final-cycle layouts cost 216. Its internal templates select 101-, 109- or 117-gas rounds from the tracked inclusive bounds, with a 109-gas final round for safe external re-entry. Across 56 rounds they cost 6,000 gas, retain one dead value per round and use two `SWAP`s per round. The older templates remain fallbacks for other bounds or layouts. The full t = 4 programs compose a fixed S-box prefix with a separately searched M4, so this search does not establish global optimality. The scheduler tries a matching full-round template before applying S-boxes, then falls back to a linear template or generic M4 when needed. Rounds may retain dead values below the required output prefix; standalone M4 block programs leave no extra values. The selected t = 4 internal program costs 166 gas, retains one dead value per round and uses three `SWAP`s. The earlier zero-SWAP schedule retained five dead values; this does not prove that every zero-SWAP program must do so. From t = 8 the same search gives the M4 of a block of the `externalD` layer (its four inputs on top, consumed, nothing left behind, with a variant that leaves the PRIME copy the internal rounds expect and one with reduced outputs for the last round), which is what lets every width from t = 8 take that layer. `huff/split.rs` cuts a permutation over the fork's code size into parts at round boundaries.

Every generated permutation lives in `huff/t<t>/Permutation.huff`. t = 4 is called through the generated hash entry `huff/t4/Poseidon2.huff` (`hash_1` / `hash_2` / `hash_3`, tested in `test/Poseidon2.t.sol`): the arity comes from calldatasize, each arity runs its own round 0 with the missing words and the capacity `n << 64` folded into its constants and its words taken from calldata as they are (the MOD, ADDMOD or MULMOD that first uses one reduces it), then jumps into the shared rounds 1 to 63, whose last linear layer computes only the returned `s0'` (row 0 of M4 straight from the S-boxes). The three cost 11,883, 11,890 and 11,963 gas. The other widths get a generated entry contract (calldata t words, returns t words) and vectors from the reference in `test/Poseidon2T<t>.t.sol`. All of them target Amsterdam (below), and `forge test` runs on an Amsterdam EVM (`evm_version = "amsterdam"` in `foundry.toml`); CI checks that the output fails on Osaka.

#### Amsterdam (EIP-8024)

`DUPN` / `SWAPN` reach stack slot 235 and EIP-7954 raises the code size limit to 65,536 bytes. The generated Huff writes them as huff-neo's `dupn n` / `swapn n` from n = 17 (immediate x encodes n = (x + 145) % 256), and the tests compile it with `hnc -e amsterdam` through foundry-huff-neo. The whole state stays on the stack; two options use the reach: `gcInternalFrom` leaves the garbage of the first internal rounds in place while the 1024 depth allows (saves the `SWAPn POP` of 5 gas per slot) and `floatPrimeInternal` reuses the nearest PRIME and supplies a fresh backing copy only when none exists or its depth exceeds half the fork's DUP reach. The refresh frequency depends on the schedule's stack growth, not just the fork. `diagPush32` keeps as many diag constants as `PUSH32` as the code size allows when the others are in memory (3 gas instead of 6 per use), on every fork. The generator finds the two limits by binary search. With `treeSums`, `internalConsume` (below) is cheaper from t = 8; t = 24 and t = 28 do not fit unrolled with every diag constant as `PUSH32`, so they take the shared body (below) with 25 and 12 steady rounds kept inline. The per-stage comparisons below describe the earlier serial-sum schedules. From t = 8 the external rounds stream as on Osaka (`externalStream`, below) with every block kept on the stack: each block runs the searched kept program with its inputs on the stack (347 gas) straight into the next round's S-boxes, so a steady external round costs t = 16 1,507 gas instead of 1,576 and t = 28 2,652 instead of 2,775 (231 gas a call at t = 8 to 867 at t = 28). The layer before the internal rounds and the last linear layer run searched programs as well (`ordered_blocks`, stacksearch `sblock` exit / exit0 / final) that leave a block's outputs on top in order, as the templates did: 152 gas a block instead of 161 (155 instead of 164 for block 0, with the PRIME copy under `s0'`) and 184 instead of 193, 36 gas a call at t = 8 to 126 at t = 28. A streamed layer pushes no floor PRIME copy: its sums and blocks DUP the nearest one, at any depth the reach allows, 3 gas a layer (the floor stays within `DUP16`, where it keeps their copies one-byte DUPs).

#### Legacy opcodes (not shipped)

For a fork before Amsterdam two things give from t = 16: the state does not fit the `DUP16` reach, and the code does not fit the 24,576 byte limit. t = 12 already has no room for garbage (12 elements, the sum and PRIME fill 14 of the 16 slots), so its internal rounds consume the old state in place (`internalConsume`): the sum chain DUPs every element in advance with the PRIME copies of its reductions between them (16 slots exactly; a copy under an element loaded from memory takes no reach, and a reduction left without a slot `DUP`s its copy on top and `SWAP2`s it under the partial sum, 3 gas more, an `ADDMOD` that still absorbs an element where a `MOD` before the `ADD` would not) and lands on a PRIME copy, so `s0^5` swapped on top of it is consumed by its own MULMOD, then every other element is SWAPped to the top and consumed by its MULMOD, its output taking the slot of the previous one, and the last ADD consumes the sum. On Amsterdam the copies of the swapped elements are pushed under the sum's own before the chain sums (`primeEarly`), so the MULMOD of `s0^5` lands m0 on them and the SWAP that put it there goes, 3 gas a round; within `DUP16` the chain sums would not reach past them. The last consuming round stacks a second copy per element and runs the next round's constant and S-box on each output as it lands over it (`externalSeam`, as t = 3 streams its seam), instead of the external round DUPing every output over a fresh copy: 3 gas a lane. Nothing is popped (26 gas per element instead of 23 plus the 5 of `SWAPn POP`). The order of the elements decides the next layout, so the last internal round takes the order that puts block 0 of the external layer back on top (an Eulerian circuit of the blocks). t = 8 fits within reach without it and keeps as many diag constants as `PUSH32` as the code budget allows. From t = 16 the stack holds 12 elements this way (or 13 or 14 with `consumeSlots`, each one more at the price of a PRIME copy of the sum chain, which the search weighs: t = 16 takes 14, t = 20 and t = 28 13) and the first indices beyond them (block 0 and whole blocks at 12, so the external layer still finds its blocks in place) live in memory: loaded for the chain and for their MULMOD and stored again (38 gas per element), with `s0^5` joining the chain from memory as well; the split parts below take this over shadowing the whole state.

- Reach: with the `shadow` schedule option a value the reach cannot `DUP` is stored to a memory slot when it is produced (`DUP1 <off> MSTORE`, 9 gas) and loaded from there (`<off> MLOAD`, 6 gas) whenever it is out of reach. Neither changes the stack, so a permissive pass first records which values need it and the real pass with the same schedule shadows exactly those (the permissive pass also records each value's last load, where the real pass frees its slot for reuse, so the memory expansion stays small; the simulation refuses a load from a reused slot). The option is only tried when no stack-only schedule works.
- Code size: `huff/split.rs` cuts the permutation at step boundaries (the initial linear layer, then one step per round) into `Part<i>.huff` contracts, as few as fit (fewer only while they cost less, since a part may fit only through the dearest schedules; a whole permutation that fits only that way is compared with the split as well), each built and checked like a whole permutation (bound tracker, reference check of its own rounds with `permutationSteps`, size check with its entry and tail).
- Linking: part i ends with the state in memory at `[0, 32t)` and `STATICCALL`s part i + 1 with it as calldata, the output lands in the same region and is returned (`returndatasize` must equal 32t). The address of the next part is the 32-byte word the deployer appends to the initcode: `NEXT_PART()` is a `PUSH32` of it (3 gas), which the generated `CONSTRUCTOR` patches into the runtime code before deploying it (the immediate ends where `HAND_OVER()`, the call itself, begins, so its offset is `__codesize(MAIN) - __codesize(HAND_OVER) - 32`), and the deployed code is the runtime alone. The generated `DeployParts.sol` next to the parts deploys a chain last to first.
- Hand-over: a part leaves lazy values below 2p (an internal round leaves `m_i + sum` with both reduced; anything above the bound is reduced before it is stored), and the next part takes them as they are: its entry loads the words without the `mod` of part 0 (8 gas per word), and an input the reach cannot `DUP` is loaded from calldata (`<off> CALLDATALOAD`, 6 gas) instead of being copied to a memory slot by the entry (9 gas each). Only part 0 reduces its calldata, so the chain is to be entered there. Part 0 (or a whole permutation) leaves the shadowed inputs out of its entry's own reach (s16 and up) in calldata, with a zero in their place (`PUSH0`, 2 gas) instead of loading, reducing and storing them (23 gas), and loads and reduces one where it is used (`[PRIME] <off> CALLDATALOAD MOD`, 14 gas against the 6 of a load); each is used twice (its column sum and its `u`), so a word saves 5 gas (t = 24 64, t = 28 84). A build that fails with them stores them instead (t = 16 has none; t = 20 keeps its stores, its schedule does not build with them).
- Shared body (`sharedBody`): a consuming round moves every output one slot deeper and the last one to the top, so after as many rounds as the stack holds elements (11 for t = 12, 12 from t = 16) the layout is back where it started, and the bounds are a fixed point after the first round. The steady internal rounds (all but the first and the last of a part) are therefore emitted once as a body of that period: a call `CODECOPY`s its round constants from a code table (`RC<i>`) into a memory scratch, stores its return label and `JUMP`s to the body, which reads each constant with `MLOAD` (3 gas more than `PUSH32`) and `JUMP`s back through the stored label; the last call falls into the body. A call of fewer rounds runs the body's last rounds: it comes before the last full call, SWAPs the stack into the layout those rounds start from (each sub-chain rotated as many places as the rounds it skips) and `JUMP`s to a mid entry, a `JUMPDEST` the full calls pass for 1 gas; where those SWAPs cost more than the 14 gas a full call would pay for a mid exit (`<off> MLOAD JUMP` to the next instruction), it leaves at a mid exit instead. The body's diag constants are `PUSH32` as it exists once, and the generator simulates every call, so the opcodes of each one are checked to be those of the first. `bodyInline` keeps as many steady rounds inline as the code size allows, or the largest count that leaves no partial call where that costs less (on Amsterdam a round inline saves 6 gas and a partial call with its mid exit costs about 18 more, so t = 24 keeps 25 rounds inline instead of 9, 66 gas less, and t = 28 12 instead of 3, 27 less).
- Sub-chains (`consumeGroup`): a body of 12 rounds is too large for the legacy code size next to the external rounds from t = 16. The consuming round can instead take the elements in sub-chains of `consumeGroup` slots (the last takes the rest): m0 takes the slot of a chain's first element, each output the slot of the next one, and the last output the first slot when m0 is swapped back on top, one `SWAP` more per chain (the last chain's close is the swap the single chain made anyway). Each chain then rotates on its own, so the period is the lcm of their lengths and the body that much shorter, at the price of the extra swaps and of more calls. When the single-chain body does not fit, the search takes the sub-chains of the longest period that does (12 = 9 + 3 gives 9, 6 + 6 gives 6, 4 + 4 + 4 gives 4), then shorter periods for as long as what their bytes buy (diag constants as `PUSH32`, inline rounds) makes each cheaper than the last (t = 28 takes a period of 3 with 25 diag constants as `PUSH32` and PRIME from memory, 297 gas less than the longest, 4); the last round of a part takes the same closes to leave every element in its block, one chain per connected component of the blocks, which is also what lets the consuming schedule build at t = 8 (after 56 rounds the layout is back where it started and the blocks are two cycles).
- PRIME from memory (`primeInMemory`): where no PRIME copy is within `DUP16` reach (the M4 blocks of an external layer, the sum chains of the first and last internal rounds) the schedule pushes one with `PUSH32` (33 bytes). Where the code size binds (sub-chains, diag constants in memory, or no fit), the search also tries storing PRIME once at a slot below the shadow slots and loading it there with `PUSH2` `MLOAD` (3 bytes, 3 gas more), keeping it when the whole schedule costs less. For t = 24 that freed 2,341 bytes for 255 gas, where a sub-chain period of 2 instead of 4 costs about 1,400 gas and each diag constant in memory 180, until the fused sums below made the code small enough without it.
- Fused sums: from 6 elements in memory (t = 24, 28) a consuming round followed by another updates them first, over the PRIME copy the sum chain leaves under the sum, and keeps each output on the stack as it stores it (`DUP1 <off> MSTORE`, into the slot its input's load freed) to add it to their sum for the next round, which is stored to one slot and joins the next sum chain as one term: 3 gas an element (a `DUP1` in place of a load) for the sum's store and load and a `SWAP` per reduction. A round whose outputs go to memory out of order (the first) sums them from their slots afterwards. At t = 28 a steady round of the body costs 18 gas less (1,153 instead of 1,171, before the `PUSH0` below) and the last internal round, which only takes the sum, 137 less; the first pays 191 more.
- `s0^5` at word 0: a consuming round with elements in memory stores `s0^5` (3 accesses a round) at word 0 of the hand-off region, which holds nothing before the last round, so its offset is a `PUSH0` (2 gas, 1 byte): 3 gas a round.
- Streamed external rounds (`externalStream`, every shadow schedule with `externalD` and the block templates; without shadow every block is kept, as on Amsterdam): shadowing each S-box output, swapping it into its input's slot (`SWAPn POP`) and loading it again for the column sums and the blocks cost 348 (t = 16) to 648 (t = 28) gas an external round over Amsterdam. Instead a layer runs block by block: the column sums `S` load the S-box outputs from memory slots, each block computes `u = x + S` on top and its M4, and each output goes straight into the next round's S-box over a PRIME copy, whose result is stored to a slot (`<off> MSTORE`, 6 gas) for the next layer to load (6 gas, twice). A block runs a searched program (`stream_blocks`, stacksearch `sblock`) that interleaves the `u`, the M4 and the S-boxes and `DUP`s the PRIME copy of each S-box under its output before computing it, instead of the `block` template followed by a `DUP` and a `SWAP` an output: a stored block costs 365 gas instead of 389 (inputs on the stack) or 377 instead of 401 (loaded), a kept one 359 instead of 386 (347 instead of 374 with its inputs on the stack). The last two blocks keep their outputs on the stack and the next layer takes them first. The S-boxes after the internal rounds store their outputs the same way, and the last round's reduced outputs go straight to their words of `[0, 32t)`, each block from the searched `final` program of Amsterdam (24 gas a call at t = 16 to 51 at t = 28; the layer before the internal rounds keeps its template, the programs' PRIME copies being out of `DUP16` reach there). A steady round costs t = 16 1,591 gas instead of 1,924 (Amsterdam 1,507) and t = 28 2,862 instead of 3,423 (Amsterdam 2,652), with no `SWAPn POP` left and smaller code.

Measured on Osaka with tree-sum, peak-aware, compact-entry and adaptive PRIME-placement candidates, t = 12 costs 35,047 gas and t = 16 uses one 24,242-byte contract at 47,809 gas. t = 20 uses one 23,884-byte contract at 61,768 gas and t = 24 one 23,946-byte contract at 74,981 gas. t = 28 fits one 24,387-byte contract at 90,740 gas after retrying with its actual entry size instead of the conservative reservation, rather than the earlier two parts (102,130 gas with a cold hop, 99,630 with a warm one). A hop costs about 2,800 gas cold: the 2,600 EIP-2929 account access (100 when warm), the state to memory and the call (about 50), the next part's entry (6 gas per word) and its memory expansion.

The constants and permutation outputs for every generated t match other implementations of the same HorizenLabs instance (gnark-crypto, TACEO, Polygon pil2). See [generator-rs/README.md](../../generator-rs/README.md#evidence-that-the-output-matches-other-implementations) for the links.

### Yul Generator

`poseidon2-gen yul` builds the Yul libraries from the same `round_constants.rs`, `reference.rs` and `value.rs`:

- `yul/program.rs` emits straight-line Yul. Every operand is a bound-tracked value whose name is the Yul text producing it (a local, a literal, an `mload` or a nested expression), so an `add` is only written where the bound allows it and the whole permutation is checked against the reference before the file is written.
- `yul/schedule.rs` orders the field operations and places the state. Internal round outputs stay lazy (below 2p) with one reduced sum per round (t = 2 keeps the sum lazy and reduces `state1` instead, so its doubling stays a shift; t = 3 adds x^5 + `state1` first so that `state2` may grow to 5p, and reduces `state1` only when the next round's x^5 + `state1` would overflow, the Huff periodic policy: 98 reductions in the internal rounds instead of 122, 222 gas less at 200 and 1,000,000 runs and 192 with the optimizer off), M4 reduces only its two inner temporaries, and the text is shaped for the legacy solc pipeline, which compiles inline assembly literally with the optimizer off: nested expressions instead of assignments, temporaries in blocks that end right after their last use, and for t = 12 a two-temporary M4 and sum chains cut so that the deepest local stays within `DUP16` / `SWAP16` (the generator models the reach of every local). The libraries are inlined into the consumer's contract with the consumer's settings, so `compat-check.sh` compiles a consumer of each library with the legacy pipeline (optimizer off, 200 runs, 1,000,000 runs) and via-IR (200 and 1,000,000 runs, t <= 4 only); CI runs it. From t = 8 a via-IR compile of the single straight-line function needs tens of GB of memory (t = 12 passed 69 GB with solc 0.8.37 before it was stopped), so t = 8 and t = 12 are for the legacy pipeline. via-IR compiles t <= 4 but turns PRIME and the diag locals back into constants at every use: with 200 runs the constant optimizer then copies each of them from code (t = 2, 3 and 4 cost 15,631, 19,577 and 37,409 gas), with 1,000,000 runs 7,560, 9,505 and 13,904 gas, the least of any setting, but the t = 4 consumer is 32,574 bytes, over the 24,576 byte limit before EIP-7954 (`compat-check.sh` prints it as WARN). via-IR does not compile t = 8 as one function: solc 0.8.30 fails a stack layout assertion ("Could not create stack layout after 1000 iterations") after 224 s and 48 GB, or passes 40 GB, so t = 8 keeps its rounds in an internal function of their own (`roundsFunction`, below), which via-IR compiles in seconds; t = 12 passes 40 GB within a minute as one function and within 10 minutes cut into functions of 8 rounds. Keeping PRIME opaque to it (`or(PRIME, shr(255, codesize()))`) did not finish compiling t = 2 in 11 minutes (over 12 GB).

t = 4 keeps `LibPoseidon2Yul` (`hash_1` / `hash_2` / `hash_3` / `poseidon2_core`) and only computes the first output of the last round. `hash_n` fold the initial linear layer and round 0's constants on [inputs, 0 .., n << 64] into four linear forms over the reduced inputs and continue in `poseidon2_rest` (the permutation from round 0's S-boxes on), which `poseidon2_core` does not call: a consumer of `hash_1` / `hash_2` / `hash_3` pays 85 / 45 / 5 gas less at 200 and 1,000,000 runs (140 / 85 / 34 with the optimizer off) for 7 / 19 / 34 more bytes, a consumer of all three about 400 more bytes, and one that also calls `poseidon2_core` carries both permutations (about 7.2 KB more). Other widths get `yul/t<t>/LibPoseidon2YulT<t>.sol` with `permute(uint256[t] memory state)`, which permutes the array in place after reducing it mod PRIME, and a test in `test/Poseidon2YulT<t>.t.sol` with the reference vectors, input sanitisation, a check that the free memory pointer and the zero slot are left as they were, and a fuzz against the Huff permutation of the same width.

The gas is above the Huff table because solc inserts a `SWAP` + `POP` per assignment and `DUP`s every operand, and because the diag constants that do not fit the code size as `PUSH32` are loaded from memory (9 gas more each). With few optimizer runs (200, the usual setting when the optimizer is on) solc's constant optimizer replaces a `PUSH32` that occurs more than once by a copy from the code (`CODECOPY` and `MLOAD`, about 25 gas more per use), so diag constants are declared as locals for the internal rounds as far as the reach allows (`diagLets`, a `DUP` instead of each `PUSH32`), two more go to the scratch space (`diagScratch`, `mload(0)` and `mload(0x20)`, 5 and 6 gas against 12 for a table entry behind a pointer) and the rest stay `PUSH32` or in the table. ## Security Considerations

The `ADDMOD` optimization, while gas-efficient, carries inherent risks related to potential `uint256` overflows if not meticulously handled. Our implementation carefully tracks "dirty" values to ensure that intermediate additions do not exceed `uint256` maximum before a modular reduction. However, it is crucial to understand that **this code has not undergone a formal third-party security audit**.
